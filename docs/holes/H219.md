# H219 — Fünf Schreibweisen von „Datei schreiben und ausführen" in EINEM Aufruf (BUG-0304; drei Mechanismen, alle in TSK-0150 geschlossen, der Rest ist benannt)

**Mechanismus.** Die Kit-Regel aus BUG-0298/H214 verweigert eine Befehlszeile, die eine Skriptdatei
schreibt und dieselbe Datei im selben Aufruf an eine Shell gibt — der Grund ist, dass jeder Haken
den TEXT des Aufrufs liest, während der Text eines Skripts bis zum Start der Shell nur Daten ist.
Fünf Schreibweisen desselben Aktes gingen an dieser Regel vorbei, weil sie an drei verschiedenen
Stellen nicht hinsah.

**Gemessene Kette** (TSK-0149, Prüfrunde 1, F2 — echte Haken-Prozesse in allen drei Kits, die echte
Shell als Schiedsrichter): `printf 'x' > run.sh ; A=1 ./run.sh`, `… ; exec ./run.sh`,
`… ; command ./run.sh`, `printf 'x' > run.sh ; bash < run.sh` und
`cat <<'EOF' > run.sh … ; eval "$(cat run.sh)"` — alle **rc 0** und alle von der Shell ausgeführt,
während die geschlossenen Formen (`; bash run.sh`, `; . run.sh`, `tee run.sh …; sh run.sh`) rc 2
waren. Kein Rückschritt der Regel: dieselben fünf waren auch vor ihr rc 0.

**Was TSK-0150 gebaut hat — drei Mechanismen, nicht fünf Schreibweisen:**

* **Das wirksame Befehlswort.** Die Regel las `stage[0]`, also das ERSTE Wort einer Stufe. Steht
  davor eine Zuweisung oder ein `exec`/`command`/`env`, ist das erste Wort nicht das Programm.
  `gate_write_scope._command_word_at` beantwortet jetzt an einer Stelle, WELCHES Wort läuft und wo
  die Operanden anfangen — beides zusammen, weil das Auseinanderziehen sofort eine Über-Verweigerung
  gekostet hat (`A=1 ./build.sh`, eine Zeile, die gar nichts schreibt, war für eine Messung lang
  rc 2; gemessen und behoben im selben Auftrag).
* **Die Eingabe-Umleitung in einen Ausführer.** `bash < run.sh` gibt der Shell das Skript über eine
  Umleitung statt als Operand, und der Operanden-Leser wirft ein Umleitungsziel absichtlich weg.
  `_executed_input_redirect_targets` liest genau das — nur ein einfaches `<`, denn `<<` öffnet ein
  Hier-Dokument, dessen nächstes Wort eine Marke ist und keine Datei.
* **Der Ausführer über eine Substitution.** `eval "$(cat run.sh)"` führt den INHALT einer Datei aus,
  die kein Operand dieser Stufe ist. `_EVALUATOR_WORDS` führt `eval`, und für eine solche Stufe gilt
  jeder Name, den ihre Wörter nennen, als ausgeführt — auch aus dem Inneren einer quotierten
  Substitution, denn genau so war die gemessene Zeile geschrieben.

**Die Alltagszeilen sind die andere Hälfte** und stehen im selben Test, weil jede der drei
Schliessungen eine davon hätte mitnehmen können: `A=1 ./build.sh`, `exec bash tools/ci.sh`,
`bash < tools/ci.sh` und `eval "$(cat tools/ci.sh)"` starten eine Datei, die dieselbe Zeile NICHT
schreibt, und bleiben rc 0.

**Gemessen:** `tools/test_hooks.py::test_the_write_and_run_rule_reads_the_effective_command_word_in_every_kit`
(fünf Verweigerungen und vier Alltagszeilen, je Kit, als echte Haken-Prozesse) und
`::test_every_evaluator_word_refuses_a_line_that_writes_what_it_evaluates` (die Mutationszeile für
die Wortliste). Rot-zuerst gesehen in einer .git-losen Kopie mit den Haken von 92d746a: alle fünf
Verweigerungen kommen als rc 0 zurück.

**Nachtrag der Prüfrunde 1 (TSK-0150, F2): ein OPTIONSWORT der Präfixe hat die Regel wieder
aufgemacht — geschlossen.** Der Leser übersprang die Präfix-WÖRTER und keine ihrer Optionen, also
wurde die Option selbst zum „Kommandowort" und das echte Programm rutschte in die Operandenrolle:
`exec -a foo bash run.sh` (macht sogar das ursprüngliche H214-Paar wieder auf), `nice -n 5 ./run.sh`,
`sudo -u me ./run.sh`, `command -p ./run.sh`, `env -i ./run.sh` — alle rc 0 gegen die VOLLSTÄNDIGE
registrierte PreToolUse-Bash-Batterie des dev-Piloten, und die echte Shell führte sie aus. Gebaut
ist die Richtung, die dieses Repo selbst schon fährt (`_harness._executed_words`): steht eine
Option da, wo das Kommandowort hingehört, ist das Kommandowort **unbekannt**, und dann gilt jeder
Operand dieser Stufe als etwas, das sie starten könnte. Dazu gehört eine zweite Hälfte, ohne die
der Alltag gebrochen wäre: Schreiben und Starten werden nur noch über VERSCHIEDENE Quellen
verglichen, sonst verweigerte sich `env -i bash tools/ci.sh` selbst. Gemessen:
`tools/test_hooks.py::test_a_prefix_words_own_option_does_not_hide_the_command_word_in_any_kit`
(sechs Verweigerungen, fünf Alltagszeilen, je Kit, als echte Haken-Prozesse).

**Was OFFEN bleibt, benannt statt gefunden — und alles davon ist die H11-Schranke** (die Datei liegt
danach auf der Platte, wo jeder Schreibzugriff, den sie dann macht, wieder beurteilt wird):

* ein Präfixwort, das die Shell überspringt und das `_command_word_at` **gar nicht** führt
  (`nohup`, `timeout`, `xargs`, `stdbuf` …). Ein solches Wort wird selbst zum Kommandowort, die
  Stufe gilt also nicht als „unbekannt", und ihre Operanden werden als geschrieben statt als
  gestartet gelesen. Das ist eine Wortliste, und dieselbe Wortliste musste im eigenen
  Gate dieses Repos (`_harness._executed_words`) schon zweimal wachsen;
* PowerShells Auswerter (`Invoke-Expression`/`iex`): absichtlich nicht in `_EVALUATOR_WORDS`, weil
  das Paar aus Schreiben und Ausführen nur auf dem POSIX-Weg gemessen ist. Ein Wort in dieser Liste,
  das niemand durch eine echte Shell getrieben hat, wäre eine Behauptung;
* die MEHRZEILIGE Form (in einem Aufruf schreiben, im nächsten starten) und ein INTERPRETER, den
  dieser Leser nicht als Ausführer führt (`python x.py`, `node x.js`) — beides schon von H214
  benannt.

**Nachtrag TSK-0152 (BUG-0305 / H220): die Über-Verweigerung dieser Richtung und ihr falscher
Satz.** Die fail-closed-Lesung der „unbekannten" Stufe liest deren Operanden auch als GESCHRIEBEN.
Darum wurde eine Stufe, die eine Datei nur LIEST, verweigert, sobald eine spätere Stufe dieselbe
Datei startet — mit dem Satz „this line WRITES …", obwohl die Zeile nichts schreibt. Die Klasse:
**eine lesende Stufe hinter einer Präfix-Option, deren Wertannahme der Leser nicht kennt, und
dieselbe Datei wird auf der Zeile gestartet.** Geschlossen für die Optionen, deren Wertannahme das
Gate jetzt KENNT (`gate_write_scope._PREFIX_OPTIONS`, dasselbe Muster wie `_compat.GIT_READER`):
dort wird das echte Programm benannt und wie jedes andere eingestuft. Für jede andere Option bleibt
die Über-Verweigerung bestehen (fail-closed), aber der Satz sagt jetzt „may WRITE" und nennt die
Option. Abgelehnt, mit Grund: „die Stufe liest nur, wenn ihre übrigen Wörter lesend sind" — das Wort
nach einer Präfix-Option kann selbst das Programm sein, und dann sind eine lesende und eine
schreibende Zeile nicht zu unterscheiden. Gemessen:
`tools/test_hooks.py::test_a_read_only_stage_behind_a_known_prefix_option_is_not_read_as_a_write`
und die Stolperdraht-Zeilen
`tools/test_hooks.py::test_every_known_prefix_option_is_needed_and_is_what_the_real_program_does`.
