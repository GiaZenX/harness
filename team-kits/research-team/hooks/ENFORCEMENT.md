# Enforcement reference — what each mechanism refuses (research-team)

The table your constitution names in §2 ("Guardrails + hard backstops") and no longer carries. It
lives here because the constitution loads at every session start and at every subagent spawn, while
this is REFERENCE: it is what you need at the moment a gate has refused a call, not before. Nothing
loads it for you — `AGENTS.md` does not import it, it is no preloaded skill, and the session-start
hook does not inject it. Every refusal a gate writes prints the path of this file, so the moment you
need the table is the moment you are handed its location.

It ships inside the hashed enforcement bundle (`.claude/hooks/`), which is what makes it as
tamper-evident as the mechanisms it describes: `guard_harness_selfmod` refuses an Edit/Write under
`.claude/hooks/`, `gate_write_scope` refuses a write-capable shell pipeline that names the layer,
and any change to this file moves the bundle hash `hook_trust` compares.

Reading a row: the left cell names the mechanism, the right cell says what it refuses and — where
the rule has one — the condition under which it does not refuse at all.

## 0. The floor under every row below

Every mechanism in this table is a hook this project REGISTERS — in `.claude/settings.json`, and
where a kit wires one per role, in that role's own file under `.claude/agents/`. A client session
that starts in a mode which does not load this project's settings loads none of those
registrations, so none of the mechanisms below RUNS in it: `project_memory/` takes ordinary
file-tool writes there, and so does `scripts/harness.py`, the entry point your constitution makes
the only way in — without moving the bundle hash `hook_trust` compares, which covers
`.claude/hooks` and `.claude/kernel` and not `scripts/`. Whether the constitution itself loads
there is the same mode's business: it was measured ABSENT in one such session, so the text that
would state this rule to you is not assured either.

This is a PROPERTY of the start mode and not one spelling of it: whatever does not load the
project settings does not load this apparatus, and an inventory of today's spellings here would go
stale the next time the client gains one. From inside a kit it is not preventable — a registration
the caller can leave out belongs to the caller. What still limits such a session depends on the
mode and is not assured here. Measured for FR-0063 / TSK-0094.

## 1. What each mechanism refuses

| Hook | Blocks / does |
|---|---|
| `guard_agent_spawn` | Claude blocks a spawn issued FROM a subagent at all (only the session instance delegates — the payload names its caller only inside a subagent, `_compat.calling_subagent`), plus generic/unnamed spawns, a second PM, missing explicit `run_in_background`, and incomplete work orders; Codex cannot veto `SubagentStart`, so exact-role policy + specialist work-order validation cover that gap. Plus (V2, spec II.4) `gate_dispatch`: no spawn without a valid `HARNESS_DISPATCH` header + live lease — missing task, wrong role, stale root revision, unproven or invalidated approval, open dependency, spent lease, missing `design_ref` for a UI task with a confirmed design; it binds the child's `agent_id` to its task. AND, on a shell call, it refuses a FAIL CLASSIFICATION (`evidence --result fail --fail-class ...`) written by anybody but the bound child of the judging class: the kernel can only see which role a lease names, so the one writer it cannot catch is the session instance typing the command while a specialist's lease is bound (DEC-0107, the user's condition that a hook measures it and the PM keeps no habit). A spawn that does not start returns the task to READY: at once on `PostToolUseFailure`, and otherwise by its bind window closing with no child (reconciled at the next spawn attempt, at `Stop`, and by `python scripts/harness.py sweep-leases`). The second half is not redundancy — measured 2026-08-02 in twelve real sessions, a spawn the permission layer refuses fires NO hook event at all, and `PermissionDenied`, which used to carry the rollback, fired in none of them. The gate spends the lease only in one chained process behind every other PreToolUse spawn gate, because a sibling's exit 2 does not stop it. AND, at the end of the LEAD's turn, it names every dispatch whose own RECORDS say no child is on it -- the child's stop was recorded at `SubagentStop`, or the dispatch window ran out with no child ever bound to it -- with what that run left in staging and the no-progress status the task's own automaton offers. A BOUND child that outlived its lease is deliberately NOT among them: a running child may outlive its lease (the lifecycle says so at `dispatch.LEASE_MINTED_STATUS`), and reporting one cost a measured false alarm whose remedy would have ended a live run. That one is a REFUSAL: on `Stop`, exit 2 does not end the turn and hands the assistant this stderr, so the finding reaches the lead instead of another "it is running" -- that is the provider's documented exit-code contract for the event, and what a real session does with it is measured in the live run and not by this repo, which has only measured that `Stop` FIRES (BUG-0058, pilot 4 P4-2, where nine consecutive waiting turns passed with a dead child and an empty staging directory). It refuses AT MOST once per finding and not at all on a stop the provider marks as one a hook already blocked, because a refused stop is answered by continuing; a second silence is therefore NOT caught, and how long that provider mark stays set is unmeasured -- a sticky one would make this silent rather than repetitive, and the task is never moved -- what to do about the finding stays the lead's. The recorder runs LAST in the `SubagentStop` chain: the gate ahead of it can turn that stop into a continuation, and a child told to keep working has not ended |
| `gate_subagent_output` | a specialist stopping without its output contract (`summary:`; the reviewer also `verdict:`). **It does NOT refuse a SECOND time**: once a stop hook has blocked this cycle the provider sets `stop_hook_active`, and blocking again would loop the subagent forever — so the retry is let through with whatever it carries, and only the audit says which of the two happened (`retry_delivered` or `gave_up`, BUG-0049). A second consecutive violation is therefore unblocked. |
| `guard_no_adhoc` + `guard_pm_scope` | the forbidden ad-hoc dump files from item 1 (PM AND code-writers); the PM writing analysis `src/**`/`tests/**`. Plus `gate_write_scope` (V2, II.4 gate 3, and §0 above bounds it as it bounds every row here): ANY tool write into `project_memory/**` (one writer, the kernel; an agent gets only `staging/<its task-id or root-id>/`), a bound specialist writing outside its `allowed_scope` and an UNBOUND subagent writing anything — both with ONE exception, rule 6: a subagent's OWN `agent-memory/<its role>/` craft topics, and only for a call whose content `guard_memory_budget` really judges (`gate_write_scope._own_craft_memory` and `guard_memory_budget.judges_this_write` are the two halves; read them there). And from a shell, when the caller is a SUBAGENT: the harness subcommands that ORDER work — creating a task, or leasing one for a spawn — and the ones that REINSTALL THE ENFORCEMENT LAYER, i.e. run the kit's installer over this project and rewrite its hooks, settings and role set. `gate_write_scope._ORDERING_COMMANDS` and `_INSTALLING_COMMANDS` are the two sets — read them there rather than from a list here — and a test derives each from the kernel's own routes — to the task producers, and to the one place the installer invocation is built — so a third command of either kind is covered the day it ships. A subagent's own `submit-result`/`evidence` stay open, and so does ASKING the user for the approval such an install needs (no command mints; the user does). Plus, for every caller, naming `project_memory` or the enforcement layer in anything but a read-only command (so copying the hooks elsewhere is refused, reading them is not). Plus, for the LEAD, a shell REDIRECT whose target is production code by the very rule `guard_pm_scope` applies to a Write — one file property, two doors, and the redirect is judged by shell syntax (`>`, `>>`, `>|`, `&>`, and the csh `>& file` that is NOT a descriptor duplication), never by a verb. Among what that rule does NOT reach — named, not closed: a write a TOOL performs from inside its own language or arguments (`cp`, `mv`, `tee`, `sed -i`, `python -c`, and the PowerShell `Out-File`/`Set-Content`/`Add-Content`/`Tee-Object` cmdlets), and a redirect target built by an expansion this process cannot resolve (`$(…)`/backticks, or a variable the same line does not assign — a same-line `F=…; > $F` IS resolved and refused). `tools/test_hooks.py::test_the_shell_writes_no_command_line_can_decide_stay_the_named_residue` and `…::test_a_powershell_cmdlet_write_is_the_named_residue_too` keep both directions honest |
| `guard_guidelines` | a code write that no active `INV` item GOVERNS — none whose `scope` names the file's language or an area containing it (item 7). WHERE it looks is the hook's own `CODE_TOP` — the conventional code directories — plus a code file at the repo ROOT; read that constant for the current set, because it is the only place the answer does not go stale. Registered in the SPECIALISTS' own frontmatter, never in `settings.json`, so it does not fire for you. What it does NOT reach: a project holding no `INV` at all (no regime yet — there the rule binds as policy), everything OUTSIDE those areas, which for this kit means `analysis/**`, `scripts/**`, `data/**`, `notebooks/**` and `tests/**` (all measured rc 0, and item 1 counts `tests/**` as analysis code), and `research_guidelines.yaml` `methods:` (the reviewer enforces that prose by reading it; no gate does) |
| `guard_question_context` | user questions referencing INVISIBLE context ("wie oben zusammengefasst" — thinking/tool calls are unseen); questions must be self-contained or preceded by visible text. Plus THREE non-blocking WARNINGS on the same event (exit 0, stderr + an audit note): a question to the user full of technical vocabulary (R2), one that asks the user for something only the MACHINE has — a git identity, the window's title bar (R2b, from a measured pilot escape), and a masterplan approval that offers no risks or objections (R13). All three are word nets over the question's own text, and that cuts both ways: a technical question phrased without such a word passes, and a PRODUCT question that uses one of them in its own sense can warn — R2b's second tier -- the words this repo has MEASURED inside a real product question, kept in the hook beside this file (`guard_question_context._AMBIGUOUS_VOCAB_RX`) and not as a copy here -- needs two hits for exactly that reason, and a single one of them no longer says anything at all. Ignore a note whose word is genuinely yours; the constitutional rule stays yours to keep either way. A question carrying the kernel's `[APR-REQ:<id>]` marker is exempt from the three, because its wording is the kernel's and must be relayed verbatim. Plus `gate_approval` (V2, spec II.2): a question marked `[APR-REQ:<id>]` must match the kernel-generated approval question EXACTLY (text, header, every option) or it is blocked; only the verbatim `Freigeben [code]` label mints the approval |
| `guard_yaml_valid` | invalid `project_memory/*.yaml` at write time — well-formedness only (parse/duplicate keys); what an item must CONTAIN is its TYPE's field contract, which the state validator answers (`python scripts/harness.py validate`) Plus `guard_memory_budget` (V2, spec II.5): a MEMORY.md index over 40 lines / 8 KB, a craft topic over 100 lines / 8 KB, any OTHER file in agent-memory over 8 KB, a 21st topic for one role, or ANY project item id in a role's memory — memory holds craft, never project status (put an id in `backticks` to quote it) |
| `gate_git` | force-push; and every merge/push whose validation **Evidence** is missing, INCOMPLETE or failing. It reads the evidence store (`evidence/`): the NEWEST `review`/`acceptance`/`test` Evidence covering an item is that kind's current verdict, so a re-run supersedes an older one and a fresh `fail` closes the gate again. `kind: audit` judges the project, not a delivery, and never opens a merge. A merge or push that NAMES a root item needs a current non-fail verdict of EVERY delivery kind, not just one: each answers a question the others do not, and the refusal says which kind is unanswered. The gate judges EVERY root id the command names, and the branch only when the command names none — an id in a commit message therefore ADDS a requirement, it never replaces the branch's. It also refuses a merge for an item still in `DRAFT` (nothing approved this work) or `REJECTED`/`SUPERSEDED` (the project dropped it). A merge that names no item anywhere binds to nothing, so it is refused while ANY item's current verdict is a `fail` — name the item in the branch (`feat/RQ-0001-…`) to be judged on that item alone — and completeness is NOT asked there: with no item to bind to, demanding every kind per subject would refuse every push while any item in the project is still mid-flight. Plus `gate_push_token` (R1): `git push` needs a user approval minted through the approval flow and bound to remote+branch+HEAD — a new commit invalidates it. That token cannot cover a FORCE push, because it binds the commit and not the remote's history, so this gate refuses one outright — on `_compat.names_force_push`, so `--force`, `-f`, `--force-with-lease` and a `+refspec` are one rule and not four (a `--dry-run` does not excuse it, and it is refused before the approval is even looked up). The same predicate decides `gate_git`'s own force refusal. Plus `gate_shell_hygiene` (R10/R11): destructive `docker` on a FOREIGN compose project or any `prune`; merge/rebase/pull/`reset --hard`/branch-switch on a dirty tree (`git add`/`stash`/`checkout -b` stay open) |
| `gate_pipeline` | merge/push unless `scripts/quality.py` actually RUNS green (incl. kit-owned `scripts/kit_checks.py`: yaml-lint, file budget) — the Research-Engineer owns/tunes the runner |
| `gate_memory_complete` | merge/push while the state validator (`python scripts/harness.py validate`) reports an error, `product/masterplan.md` is still the raw template, or `project_config.yaml` has no project name / only TODO stacks |
| `gate_test_scope` | a shell line that runs the WHOLE test surface the project DECLARED, unless the line itself says it is the delivery run (`DELIVERY_RUN=<ITEM-ID>` in front of the runner, or PowerShell's `$env:DELIVERY_RUN="<ITEM-ID>";` before it) -- and then only once per item: a second whole-surface run for an item that already holds a PASSING Evidence with `run_scope: full` is refused too, while one whose full run FAILED is not, because findings are what sends the work back into the tests. **It does not refuse at all** where the project declares no test surface: applicability comes from an `INV` item with `scope: test_surface` (the same knob mechanism `scripts/kit_checks.py` reads), so a runner nobody declared is not judged, and neither is a declared surface whose measured `seconds` is at or under that item's `judged_above_seconds`. A selection -- a sub-path, a node id, or an option the item lists under `options_that_narrow` -- passes untouched. The occasion is measured rather than feared: repeating a whole suite on every task cost one project's rounds about four hours with no finding out of any of those runs, which is why the rule is 'the tests that read what you changed during the work, the whole surface once before delivery'. What it cannot see is a runner the text does not fix (`$RUNNER tests/`), and an option that narrows the run and is NOT declared -- that line reads as a full run and is refused, which is over-refusal and answered on the line |
| `guard_scratchpad_ref` | repo source files referencing ephemeral session-scratchpad paths |
| `guard_harness_selfmod` | Claude hard-blocks edits to `.claude` enforcement; Codex blocks through trusted `PreToolUse` plus read-only permission-profile paths, with CI as a research backstop |
| `notify_agent_events` | (never blocks) logs agent lifecycle (Notification + SubagentStop) to `project_memory/.audit/hook_events.jsonl` |
| `format_on_write` / `session_status` / `kit_trust_state` / `clear_handover_marker` | best-effort formatting / session-start briefing + kit-update banner & escalating pending nag & version-change announcement & model/effort sync nag / records which hook bundle this project trusts in `.claude/kit_state.json` (`restart_required` -> `active`; `hooks_trust_required` when the bundle changed) -- doctor measures `hook_trust` against it, and `gate_dispatch` REFUSES every specialist spawn while the installed bundle is not the recorded one (it compares the hashes itself, so a bundle changed mid-session counts too; `restart_required` is not that case and delegation stays open there). ANY difference counts, a stray `.pyc` cached into `.claude/kernel/__pycache__` included -- measured: one such file stops every delegation, and removing that `__pycache__` directory restores the recorded hash on its own (bytecode is not part of what the scaffold installs). A project carrying NO `kit_state.json` has nothing to compare and is not stopped. Touching the record is refused on every route that NAMES the layer -- Edit/Write by `guard_harness_selfmod`, and a shell pipeline by `gate_write_scope` (measured for `rm`, `rm -f`, `del`, `Remove-Item`, an inline `os.remove` and `cd .claude && rm`). What still gets through is the complement: a command line that names it NOWHERE -- a glob, `find`, `git clean -xfd`, or a script the agent runs. That route can not only DELETE the record but REWRITE it with the hash of an already-tampered bundle, and a re-blessed bundle is then indistinguishable from an untouched one (measured: one byte appended to a hook -> spawn refused; the same command line re-blessing the record -> refusal gone). `kit_state.json` cannot live inside the hashed set, because it holds that set's hash -- so this is a limit of the record, and the reason `hook_trust` is a doctor CAPABILITY and not a proof / (never blocks) clears the BUG-0016 handover marker (`.claude/HANDOVER_PENDING`) on a genuine restart (`source=startup`), never on a resume/reconnect -- the marker is what the GLOBAL `~/.claude/hooks/handover_guard.py` reads to refuse product-code writes and derivation in the entry session (DEC-0032) |
